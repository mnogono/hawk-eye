# HAWK-EYE Phoenix — техническая спецификация

Черновик. Документ для разработки: здесь фиксируются технические решения. Что и когда получает заказчик — в `roadmap.md`.

Статусы пунктов: **Решено** — утверждено; **Предложение** — ещё не утверждено; **Открыто** — нужно решение.

## 1. Архитектура

**Решено.** Одно приложение Spring Boot: веб-интерфейс и работа с прибором (опрос, сбор данных, выполнение последовательностей) — в одном процессе. В старой версии это два процесса (`vdbMain.exe` и `vdbMainService.exe`), которые общаются через таблицу `cmd_queue` в БД; в новой версии этого разделения нет.

**Решено.** Инструмент миграции данных — отдельная программа, которую запускает оператор (не часть веб-приложения).

**Решено.** Пользователи и авторизация.
- Система пользователей закладывается с версии 0.1: учётные записи хранятся в БД, приложение с самого начала работает с текущим пользователем.
- По умолчанию авторизация — anonymous: вход без логина и пароля, все работают как анонимный пользователь.
- Вход по логину и паролю — в версии 1.0; включается в настройках, по умолчанию выключен.

**Предложение.** Spring Security с первой версии; anonymous-режим — его штатная анонимная аутентификация, поэтому включение входа в 1.0 не меняет контроллеры и шаблоны.

**Предложение.** Модули приложения (Java-пакеты):

| Модуль | Ответственность |
|---|---|
| `instrument` | Клиент Sparx API, драйверы узлов прибора, опрос состояния |
| `acquisition` | Выполнение методов и последовательностей, сбор данных |
| `live` | Буфер живых данных в памяти, рассылка по SSE |
| `data` | Сущности, репозитории, доступ к PostgreSQL |
| `processing` | Калибровка, расчёты, контроль качества |
| `reports` | Генерация отчётов |
| `web` | Контроллеры, шаблоны Thymeleaf |
| `migration` | Отдельная программа переноса данных из MSSQL |

## 3. Фронтенд

### 3.1. Сборка

**Решено.**
- Vite собирает и минифицирует TypeScript и Sass; зависимости — из npm.
- frontend-maven-plugin скачивает Node.js внутрь проекта и запускает сборку фронтенда при `mvn package`. Разработчику не нужно ставить Node отдельно.
- Сброс кэша браузера — Spring `VersionResourceResolver` со стратегией по содержимому (хеш в имени файла). Vite выдаёт файлы с постоянными именами; связывать шаблоны с манифестом Vite не нужно.
- Режим разработки: `vite build --watch` и Spring Boot DevTools.

### 3.2. Свои компоненты

**Решено.** Веб-компоненты (custom elements) на TypeScript, без фреймворка: `<hawk-live-chart>`, `<hawk-sample-table>`, `<hawk-zone-editor>` и т. д. Браузер сам инициализирует компонент, когда htmx вставляет его в страницу, — повторная инициализация после подмены фрагмента не нужна. В шаблоне Thymeleaf компонент — обычный тег с атрибутами; Chart.js, SSE и Tabulator спрятаны внутри.

### 3.3. Оформление

**Решено.**
- Bootstrap 5.3; тема — через переменные Sass (палитра, шрифт, отступы), подключаются только нужные части Bootstrap.
- Для плотных экранов (редактор методов, ручное управление) — компактные размеры: `form-control-sm`, `btn-sm`, `table-sm`.
- Светлая и тёмная темы — `data-bs-theme`.
- Выпадающие списки с поиском и множественным выбором — Tom Select поверх обычного `<select>`; варианты для длинных списков (проект, скважина) подгружаются с сервера.
- Модальные окна — Bootstrap Modal, содержимое подгружается через htmx. Уведомления — Toast.

| Элемент | Чем |
|---|---|
| Кнопки | `btn` |
| Поля ввода | `form-control` |
| Текстовые поля | `textarea.form-control` |
| Выпадающие списки | `form-select`; с поиском — Tom Select |
| Окна, подтверждения | Bootstrap Modal |
| Уведомления | Bootstrap Toast |
| Иконки | SVG-спрайт (см. 3.4) |

### 3.4. Иконки

**Решено.**
- Иконки только как SVG-спрайт; шрифт Bootstrap Icons не подключаем.
- Сборка кладёт в спрайт только используемые Bootstrap Icons (из `node_modules/bootstrap-icons/icons/`) и свои иконки. Список используемых иконок ведётся в конфигурации сборки.
- Свои иконки — в стиле Bootstrap Icons: `viewBox="0 0 16 16"`, один цвет `fill="currentColor"`, линии около 1 px.
- В шаблонах — фрагмент Thymeleaf; в JS-компонентах — функция `icon(name)`, которая собирает такой же `<svg><use>`:

```html
<!-- fragments/icon.html -->
<svg th:fragment="icon(name)" class="bi" width="1em" height="1em" fill="currentColor">
  <use th:href="@{/icons/icons.svg} + '#' + ${name}"/>
</svg>

<svg th:replace="~{fragments/icon :: icon('crucible')}"></svg>
```

- Встроенный SVG — только для разовых случаев (логотип).

### 3.5. Адреса страниц (URL)

**Решено.** Данные доступны по ссылке: у каждого ресурса — образца (`sample`), метода (`method`) и т. д. — свой постоянный адрес. Ссылку можно сохранить в закладки или отправить коллеге; по ней открываются те же данные.

**Предложение.**
- Вид адресов: список — `/samples`, запись — `/samples/{id}`; так же `/methods`, `/methods/{id}` и остальные ресурсы.
- Фильтры, сортировка и страница списка — в параметрах адреса (`/samples?method=12&sort=-date`), чтобы ссылка открывала ту же выборку. Когда htmx меняет часть страницы, адрес в браузере обновляется (`hx-push-url`).
- Если вход по логину включён (раздел 1), ссылка без входа в систему ведёт на страницу входа, после входа — на исходный адрес.

## 4. Графики и живые данные

### 4.1. Исходные данные

- Прибор отдаёт данные с частотой 10 Гц (`sparx_api.js:2005` в старой версии).
- Окно онлайн-графика по умолчанию — 10 минут, настраивается; в старой версии в памяти хранится до 60 минут (`max_online_data_stored_minutes`).

| График | Точек на кривую |
|---|---|
| Скользящее окно 10 мин | 6 000 |
| Скользящее окно 60 мин | 36 000 |
| Кривые анализа, накапливаются с начала анализа | 12 000–36 000 (анализ 20–60 мин) |

### 4.2. Доставка данных (SSE)

**Решено.**
- Сервер держит кольцевой буфер последних N минут в памяти и рассылает обновления через SSE (`SseEmitter`).
- Браузер при открытии страницы или переподключении забирает накопленную историю одним запросом, затем получает только новые точки — пачками раз в 0,5–1 с.
- Все вкладки и все пользователи получают одни и те же данные; прибор опрашивает только сервер.

### 4.3. Chart.js

**Решено.** Chart.js для всех графиков: живые данные, кривые анализа, просмотр образцов, редактор зон.

- Анимация выключена; данные передаются упорядоченными и готовыми (`parsing: false`, `normalized: true`).
- Перерисовка — по пачке, `chart.update('none')`; не на каждую точку.
- Прореживание (decimation) — алгоритм **min-max** (сохраняет вершины пиков), не LTTB.
- Скользящее окно: точки добавляются в конец, точки старше окна удаляются из начала, границы оси X сдвигаются.
- Накапливающийся график: точки только добавляются, ось X растёт.
- Ось X — минуты от начала анализа, числовая ось (адаптер дат не нужен).
- Две оси Y: сигнал детектора и температура.
- Масштабирование — `chartjs-plugin-zoom`; зоны и их границы — `chartjs-plugin-annotation`; перетаскивание границ зон — своя надстройка над annotation.

## 5. Таблица образцов

**Решено.** Tabulator.

- Бесконечная прокрутка с подгрузкой (`progressiveLoad: "scroll"`), в DOM только видимые строки.
- Фильтрация и сортировка — на сервере (`filterMode: "remote"`, `sortMode: "remote"`).
- Постраничная выборка — **keyset**, не `OFFSET`: `WHERE (sort_key, id) > (:last_sort_key, :last_id) ORDER BY sort_key, id LIMIT :page_size`.
- Индексы — под основные сортировки и фильтры: дата, имя образца, проект и скважина, метод.
- Объём: в базах заказчика — десятки тысяч образцов. Общее число найденных строк считается точно.
- Настройка колонок (порядок, ширина, видимость, запоминание) — средствами Tabulator; этим закрывается «Sample table column editor» из версии 1.0.
- Тема — `tabulator_bootstrap5`.

## 6. Связь с прибором

**Решено.** Плата Sparx: JSON-RPC 2.0 поверх HTTP POST.

- Методы API (из старой версии, `objects_ex/modules/pcb/sparx/sparx_api.js`): `exec_command`, `exec_watlow_command`, `exec_pedestal_command`, `exec_autoloader_command`, `exec_acq_command`, `get_acq_data`, `get_sensors_status`, `get_devices`, `heartbeat`.
- Узлы прибора: печь, регуляторы температуры Watlow, пьедестал, термопары, регуляторы расхода газа, дисплей EPC, автозагрузчик.
- Автозагрузчик EzAxis: ASCII-команды (`documents/Command_Set_EZHR17EN.pdf`) передаются в hex через `exec_autoloader_command`.
- Описание протокола: `documents/Comm Protocol*.pdf`, `documents/HAWK API.docx` в старом репозитории.

**Открыто.** Старая версия поддерживает и предыдущее поколение плат — Wildcat (TCP к NetBurner, автозагрузчик по COM-порту). Нужна ли поддержка Wildcat в новой версии? В `roadmap.md` её сейчас нет.

## 7. Эмулятор Sparx

**Решено.** Для разработки и автотестов используется существующий эмулятор из старого репозитория, без переписывания:
- `instrument/sparx/server.py` — эмулятор платы, JSON-RPC на `127.0.0.1:10000`; состояние — `hawk_instrument.py`; параметры командной строки задают состояние тигля, Watlow и водорода;
- `instrument/sparx/epc_display.py` — эмулятор дисплея EPC, порт 20000.

Автотесты запускают эмулятор как внешний процесс и останавливают его после прогона.

**Решено.** Эмулятор запускается на Python 3: venv в старом репозитории (`instrument/venv`) собран на Python 3.10, зависимости — `instrument/sparx/requirements.txt`. Упоминания Python 2.7 в README и `server.cmd` старой версии устарели (`Werkzeug==2.0.1` на 2.7 не устанавливается).

**Открыто.** На машине разработки Python 3 сейчас не установлен; запуск эмулятора ещё не проверен.

## 8. Данные

### 8.1. PostgreSQL

**Решено.** PostgreSQL вместо Microsoft SQL Server Express (лимит базы 10 ГБ).

**Решено.** Переработка структуры при переносе (из исходной дорожной карты):
- настройки кривых и словари, которые сейчас хранятся упакованными, становятся обычными реляционными таблицами;
- калибровка: коэффициенты — в отдельную таблицу; убрать поля `calibration_over_r_xxx` и `calibration_oven_t_xxx`; убрать `calibration_coefficients`; переработать `calibration_sensor_data` (нужна только для калибровки POPI);
- пересмотреть `calibration_curves`, `cm_cat_param`, `cm_category`, `cm_compos_log_comment`, `cm_conf` и остальные таблицы.

Исходная БД: MSSQL `hawk_v1_0`, 42 таблицы (`server/data/create_sql_db.sql` в старом репозитории); служебные поля `vdb_id/vdb_rec/vdb_cdate/vdb_edate/vdb_sid`; системные EAV-таблицы `vdb_*`.

**Решено.** PostgreSQL 18 — последняя стабильная версия (вышла в сентябре 2025, поддержка до ноября 2030). Есть официальные сборки для Windows, основных дистрибутивов Linux и macOS. PostgreSQL 19 на октябрь 2026 ещё в бете: в момент выхода у неё не будет пакетов во всех дистрибутивах. Переход на 19 рассмотреть ближе к выпуску 1.0. Обновление основной версии у заказчика требует `pg_upgrade` или выгрузки и загрузки базы.

**Решено.** Заказчик устанавливает PostgreSQL сам, отдельно от приложения; установщик приложения PostgreSQL не содержит. Нужна пошаговая инструкция: установка PostgreSQL 18, создание базы и пользователя для HAWK-EYE. Параметры подключения (хост, порт, база, пользователь, пароль) задаются при установке приложения или при первом запуске. PostgreSQL нужен начиная с версии 0.1 (там хранятся настройки прибора).

### 8.2. Миграция

**Решено.** Отдельная программа, запускается оператором; переносит существующую базу HAWK-EYE в новую структуру. Тестируется на копиях реальных баз.

### 8.3. Бэкап

**Решено.** Создание бэкапа — из приложения; восстановление — по пошаговой инструкции.

**Предложение.** Бэкап создаётся через `pg_dump` из установки PostgreSQL заказчика: путь к утилите — в настройках приложения, по умолчанию определяется автоматически. Версия `pg_dump` должна быть не ниже версии сервера. Если база стоит на другом компьютере, на компьютере с приложением нужны клиентские утилиты PostgreSQL 18.

### 8.4. Обновление структуры БД

**Решено.** Liquibase — единственный способ создавать и менять структуру базы. Вручную структуру не меняем.

**Предложение.**
- Главный changelog — `db/changelog/db.changelog-master.yaml`; changeset'ы разложены по версиям приложения (`0.1/`, `0.2/`, …) и подключаются через `includeAll`. Формат changeset'ов — formatted SQL: база только PostgreSQL, обычный SQL проще читать и проверять.
- Автозапуск Liquibase в Spring Boot выключен (`spring.liquibase.enabled=false`). Приложение запускает обновление само при старте, в таком порядке:
  1. если есть неприменённые changeset'ы — сначала бэкап базы (`pg_dump`, раздел 8.3);
  2. применение changeset'ов;
  3. если в `DATABASECHANGELOG` есть changeset'ы, которых эта версия не знает, приложение не запускается: база обновлена более новой версией.
- Мастер первого запуска создаёт структуру пустой базы теми же changeset'ами; инструмент миграции из MSSQL — тоже. Источник структуры БД один.
- Тесты: все changeset'ы применяются к пустому PostgreSQL 18 (Testcontainers), а также обновление базы предыдущей версии до текущей.

**Лицензия.** Liquibase Community с версии 5.0 распространяется по Functional Source License (FSL-1.1-ALv2), а не по Apache 2.0; каждый выпуск через два года переходит на Apache 2.0. FSL разрешает бесплатное использование в продакшене, в том числе внутри своего продукта; запрещено только коммерческое использование, конкурирующее с самим Liquibase. HAWK-EYE с Liquibase не конкурирует. Но FSL не входит в число лицензий, одобренных OSI: если юристы заказчика требуют только OSI-лицензии в составе распространяемой программы, нужно брать последнюю ветку 4.x (Apache 2.0).

**Открыто.** Устраивает ли заказчика лицензия FSL у Liquibase 5.x — или берём 4.x.

## 10. Тестирование

**Решено.** Автотесты обязательны в каждой версии и входят в её срок. Версия готова, только когда проходят её тесты и тесты всех предыдущих версий. Покрывается:
- алгоритмы — калибровка, расчёт, контроль качества, обработка данных сбора; результаты сверяются с результатами старого HAWK-EYE на эталонных наборах данных от заказчика;
- операции создания, чтения, изменения и удаления для всех типов записей;
- сериализация и десериализация — настройки, методы, кривые, сообщения протокола прибора, файлы импорта и экспорта;
- миграция данных — на копиях реальных баз;
- создание бэкапа и восстановление из него;
- связь с прибором — на эмуляторе Sparx;
- логика своих фронтенд-компонентов — Vitest (скользящее окно графика, перетаскивание границ зон, разбор данных SSE);
- остальной основной функционал, который можно проверить кодом.

## 11. Платформы, установка и обновления

### 11.1. Платформы

**Решено.** Целевая ОС — Windows. Linux в первом приближении не собираем и не тестируем, но технологии выбираются так, чтобы перейти на Linux можно было без переписывания. Другие ОС — решать при необходимости.

Правила переносимости:
- никаких Windows-специфичных API в Java-коде (реестр, JNA, WMI); всё платформенное — служба, установщик, ярлыки — изолировано в `distribution/windows`;
- пути — через `java.nio.file.Path`; каталоги конфигурации, данных и логов задаются настройкой, не зашиты;
- имена файлов ресурсов и шаблонов — с точным регистром (в Linux файловая система чувствительна к регистру);
- путь к утилитам PostgreSQL (`pg_dump`) — настройкой;
- отчёты не зависят от шрифтов Windows: нужные шрифты поставляются с приложением;
- связь с прибором Sparx — по HTTP, переносима. Плата Wildcat работала через COM-порт — если её понадобится поддержать, это место потребует отдельного внимания.

### 11.2. Установка

**Решено.** Для Windows — установщик Inno Setup. Java внутри (`jlink`); PostgreSQL не входит, заказчик ставит его сам по инструкции. Заказчик получает исходный код и сам распространяет программу, поэтому установщик должен собираться у него из исходников.

**Предложение.**
- Настройка — в самом приложении: мастер первого запуска в браузере (подключение к PostgreSQL с проверкой, создание таблиц, первый администратор). Установщик делает только платформенную часть: копирует файлы, регистрирует службу, создаёт ярлык и правило брандмауэра. Так установщик остаётся тонким, а мастер пригодится и для Linux.
- Приложение работает как служба Windows (обёртка WinSW): стартует вместе с компьютером без входа пользователя — нужно для ночных последовательностей.
- Сборка `setup.exe` — отдельным профилем Maven на Windows-машине с Inno Setup. Цифровая подпись (сертификат заказчика) добавляется одним параметром сборки; без подписи Windows SmartScreen предупреждает о неизвестном издателе.

### 11.3. Обновления

**Решено.** Автообновления и онлайн-проверки обновлений нет: на компьютерах клиентов, как правило, нет интернета. Обновление — новый `setup.exe`, который заказчик передаёт клиенту (ссылка, почта, флешка); клиент запускает его поверх установленной версии.

**Предложение.**

Раскладка на диске:
- программа и Java — `C:\Program Files\HAWK-EYE Phoenix\`, заменяется при обновлении;
- настройки и логи — `C:\ProgramData\HAWK-EYE Phoenix\`, при обновлении и удалении программы не трогаются.

Порядок обновления:
1. Установщик спрашивает у работающего приложения его состояние (локальный HTTP-запрос). Если идёт анализ или последовательность — установщик сообщает об этом и предлагает повторить позже; службу не останавливает.
2. Остановка службы, замена файлов программы, запуск службы.
3. При старте приложение обновляет структуру БД через Liquibase: если есть неприменённые changeset'ы — сначала бэкап базы (`pg_dump`), затем changeset'ы (раздел 8.4).
4. Приложение не запускается на базе, которую уже обновила более новая версия (защита от установки старой версии поверх новой базы).
5. Номер версии виден в интерфейсе (окно «About» и страница администратора).

Откат — установка предыдущего `setup.exe` и восстановление бэкапа, сделанного перед миграцией, по инструкции.

Укладывается в текущие оценки: установщик — неделя «Installer» в 0.1; Liquibase и бэкап перед обновлением структуры — вместе с новой структурой БД в 0.2.

Не закладываем: загрузку пакета обновления через страницу администратора, онлайн-проверку, корпоративное развёртывание (MSI, SCCM/Intune) — можно добавить, если клиенты заказчика попросят.

## 13. Открытые вопросы

1. Поддержка плат Wildcat (раздел 6).
2. Установить Python 3 и проверить запуск эмулятора Sparx (раздел 7).
3. Создание бэкапа через `pg_dump` — подтвердить (раздел 8.3).
4. Библиотека генерации отчётов (раздел 9).
5. Экраны старой версии, которых нет в дорожной карте: калибровка температуры образца, статическая и динамическая калибровка печи, журналы прибора и событий, обслуживание, статистика прибора, тесты Watlow и системы.
6. Нужно ли управлять шагами сбора данных из интерфейса.
7. Лицензия Liquibase 5.x (FSL) — устраивает ли заказчика, или берём 4.x (раздел 8.4).
